El concepto

Qué es y por qué existe

CashDroController es una aplicación de consola para Windows que opera un reciclador de efectivo CashDro: cobrar, anular una operación, consultar estado, niveles y alarmas. Cuatro módulos separan configuración, cliente HTTP, API del equipo y menú; el flujo de cobro sondea el estado del dispositivo, contempla cancelación con Ctrl+C en dos pasos y reintenta solo cuando el equipo responde que está ocupado.

Está pensada para diagnóstico y automatización en una caja que ya tiene el hardware pero no quiere depender del SDK del fabricante. El valor está en el método: el contrato se reconstruyó desde el manual de integración, cada error de aplicación se separó del error de transporte y los céntimos se manejan como enteros. La limitación principal es la misma que su origen: no hubo equipo disponible para validar.

03 — La idea

El efectivo también necesita una API

Un CashDro no es una caja registradora: es un periférico con estado, niveles y operaciones asíncronas. Esta consola lo opera sin esconder esa complejidad.

El problema

Las operaciones con efectivo tienen estados intermedios: la máquina acepta, clasifica, recicla y confirma. Una integración naive consulta una vez y asume que todo salió bien. El resultado son descuadres y tickets sin sustento.

La solución

Una consola que modela el ciclo completo: autenticación, venta, polling de estado, reintentos ante System busy y consulta de niveles. Cada operación deja un resultado legible para el operador.

05 — Bajo el capó

Una consola, un protocolo

La lógica de negocio vive en la consola; el CashDro solo expone su API.

Polling con timeout

No se asume éxito: se consulta el estado hasta una condición final o un límite de tiempo.

Reintentos selectivos

Solo los errores recuperables, como System busy, se reintentan.

Operación visible

Cada paso se muestra en la consola para que el operador sepa qué está pasando.

Lo que no funcionó

Los tropiezos, documentados

Las primeras versiones existen para que estos errores no se repitan: cada una dejó una decisión de diseño verificable.

CashDroController

System busy tratado como caída de red

Cuando el CashDro respondía -1900, el mensaje final era «Error de conexión tras 3 intentos: None», sin código ni explicación: el error de aplicación caía en el camino del error de transporte. Se agregó un contador propio para -1900 con espera de cinco segundos y un mensaje explícito.

CashDroController

Contadores de reintento que se pisaban

Un único contador cubría fallos de red y respuestas de equipo ocupado, así que cada condición consumía los reintentos de la otra. Se separaron en dos variables. Al documentarlo se descubrió que el continue del -1900 también consume iteración: con tres reintentos el máximo real es tres peticiones, no seis.

CashDroController

JSON anidado de forma variable

startOperation devolvía «No se recibió operationId» con code 1 porque el firmware anidaba la respuesta un nivel más: response.operation.operation.operationId. Se normalizó en el borde de cada método que lee el contrato. La tolerancia cubre un nivel extra; un tercer nivel no está contemplado.

CashDroController

Credenciales de ejemplo en el repositorio

El proyecto se desarrolló contra una instalación concreta y la IP, el usuario y la contraseña quedaron en config.py y en el script de lanzamiento. Los valores pasaron a variables de entorno con marcadores 192.0.2.10 y cashdro.sh quedó pendiente de parametrizar o excluir.
